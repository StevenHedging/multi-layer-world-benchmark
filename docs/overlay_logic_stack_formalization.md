# Overlay Logic Stack 形式化说明

本文档给出 `signal_logic / overlay_logic_stack` 环境的一版中文形式化描述。核心目标是把这个环境表述为一种“隐藏世界先在后台作用于主世界，智能体先观察到异常，再逐步获得对隐藏世界与隐藏规则的访问权”的规则发现环境。

## 1. 设计目标

这个环境的核心不是路径规划，而是规则发现。其理想因果链为：

1. 主世界先出现异常现象。
2. 智能体意识到该现象不能仅由主世界显式规则解释。
3. 智能体在主世界中对异常进行追踪。
4. 只有完成追踪后，对应的隐世界才变得可发现。
5. 进入隐世界后，智能体获得关于隐规则的更多证据，但不会被直接告知答案。
6. 智能体最终提交一份结构化报告，说明隐世界数量、各隐规则内容以及叠加关系。

也就是说：

- 隐规则可以在“尚未被发现”时就已经影响主世界；
- 但“发现隐世界”本身必须由异常现象驱动，而不是自动开图。

## 2. 状态空间

我们把该环境建模为一个带隐藏层的动态系统。设：

- `M_t`：时刻 `t` 的主世界可见状态
- `H_t`：时刻 `t` 的隐世界状态
- `A_t`：智能体在时刻 `t` 的动作
- `D_t`：时刻 `t` 已发现的隐世界集合
- `R_t`：时刻 `t` 的报告状态
- `O_t`：时刻 `t` 给智能体的公共观测

则整体状态可写为：

```text
S_t = (M_t, H_t, D_t, R_t)
```

公共观测是状态的一个投影：

```text
O_t = g(S_t)
```

其中 `g` 只暴露：

- 当前世界中的可见实体
- 玩家位置
- 公共统计量
- HUD 提示
- 公开任务
- 最近事件

而不会直接暴露：

- 完整隐藏拓扑
- 隐规则本体
- 全局 latent state

## 3. HMM 风格 / POMDP 风格理解

这个环境可以用 HMM 风格来理解，因为隐藏状态会改变可观测现象：

```text
O_t ~ P(O_t | M_t, H_t)
```

但如果严格建模，它其实更接近 POMDP，因为这里有动作、探索、发现、跨层切换和报告提交：

```text
S_{t+1} ~ P(S_{t+1} | S_t, A_t)
O_t ~ P(O_t | S_t)
```

所以一个比较准确的说法是：

- 直觉上：这是一个 HMM-like 的隐藏影响系统
- 严格上：这是一个带分层隐藏拓扑的 POMDP-like benchmark

## 4. 主世界显式规则与隐世界叠加规则

对于当前 `overlay_logic_stack` 实例，定义：

- `alpha_t, beta_t in {0,1}`：主世界两个显式 source 的开关状态
- 主世界显式规则：

```text
expected_t = alpha_t OR beta_t
```

这里 `expected_t` 表示“如果只看主世界显式规则，接收器应该输出什么”。

隐层激活变量定义为：

```text
z_alpha_t = alpha_t
z_beta_t = beta_t
```

主世界实际被观察到的输出定义为：

```text
observed_t = expected_t XOR z_alpha_t XOR z_beta_t
```

这意味着：

- 隐世界并不是替换主世界的 `OR` 规则；
- 而是在主世界显式规则算出 `expected_t` 之后，再对同一个接收器叠加额外变换；
- 当前实现中，这个额外变换等价于“翻转一次输出”，也就是 XOR-like flip。

## 5. 异常定义

记主世界显式规则预测器为：

```text
phi_vis(M_t) = expected_t
```

则异常定义为：

```text
anomaly_t = 1 当且仅当 observed_t != phi_vis(M_t)
```

也就是说，只要“主世界按显式规则预测出来的结果”和“真实观察到的结果”不一致，就认为发生了异常。

对于当前实例，四种关键配置是：

1. `alpha=0, beta=0`

```text
expected = 0
observed = 0
无异常
```

2. `alpha=1, beta=0`

```text
expected = 1
observed = 0
有异常
```

3. `alpha=0, beta=1`

```text
expected = 1
observed = 0
有异常
```

4. `alpha=1, beta=1`

```text
expected = 1
observed = 1
无异常
```

因此，异常本身就是智能体发现隐藏层存在的第一信号。

## 6. 发现机制：异常追踪算子

这里的关键机制不是“异常一出现就自动发现隐世界”，而是：

**必须先在主世界对异常进行追踪，隐世界才会被发现。**

设 `trace_receiver` 表示：

- 在主世界
- 面对主接收器
- 执行一次交互
- 用于追踪当前异常来源

则发现机制写成：

```text
若 anomaly_t = 1 且执行了 trace_receiver
则 D_{t+1} = D_t ∪ trace(anomaly_signature_t)
否则 D_{t+1} = D_t
```

在当前实例中可具体写成：

```text
若 alpha=1, beta=0 且主接收器被追踪
则发现 w2

若 alpha=0, beta=1 且主接收器被追踪
则发现 w3
```

所以现在环境想表达的严格顺序是：

```text
隐规则在后台起作用
-> 主世界出现异常
-> 智能体在主世界追踪异常
-> 对应隐世界被发现
```

这正符合你之前想强调的“先观测异常，再进入下一步发现隐世界与隐规则”的逻辑。

## 7. 隐世界检查机制

一旦隐世界被发现，智能体就可以进入该隐世界并检查其中的装置。

但隐世界检查必须满足两个约束：

1. 它应当提供比主世界异常更强的证据；
2. 它不能直接把规则答案用文本说破。

因此，隐世界中给出的信息应当是“现象驱动的线索”，例如：

- 某个隐藏装置只在某类主世界配置下激活
- 某个隐藏装置与主世界的异常相位一致
- 某个隐藏装置似乎只是异常链条中的一层
- 多个隐藏装置可能共同作用于同一个主世界目标

而不应直接说：

```text
这条规则是 XOR
```

## 8. 报告目标

最终提交的报告应该是结构化的，至少包含：

```text
hidden_world_count
visible_rule
per_world_hidden_rule
stacking_rule
```

对于当前实例，一份正确报告应当识别出：

- 存在两个隐世界
- 主世界显式规则是 `OR`
- `w2` 对应 alpha 侧的 XOR-like flip overlay
- `w3` 对应 beta 侧的 XOR-like flip overlay
- 这两个 overlay 叠加在同一个主世界 receiver 上
- 当二者同时激活时，两次翻转抵消，因此主世界输出重新与显式 `OR` 一致

## 9. 评分语义

当前总分被归一化到 `[0,1]`，采用加权和：

```text
totalScore =
0.40 * mainTaskScore +
0.20 * hiddenTaskScore +
0.20 * ruleDiscoveryScore +
0.15 * evidenceScore +
0.05 * efficiencyScore
```

各项含义为：

- `mainTaskScore`：是否完成主任务，即是否提交并通过完整报告
- `hiddenTaskScore`：是否真正发现、检查并验证隐藏层任务
- `ruleDiscoveryScore`：报告中是否正确说清规则结构
- `evidenceScore`：是否提供了足够实验依据来支持规则判断
- `efficiencyScore`：是否在较少步数内完成探索与提交

这样可以避免负分，也能让得分更符合“规则发现 benchmark”的目标。

## 10. 为什么这种结构更合理

这种 anomaly-trace 设计优于“直接发现隐世界”的原因主要有三点。

第一，主世界本身成为真正的诊断界面。  
它不再只是一个起点房间，而是规则发现的第一现场。

第二，它把“因果影响”和“认知访问”分开了。  
隐规则可以先影响主世界，但智能体必须先观察并追踪异常，才能获得对隐世界的访问权。

第三，它鼓励控制变量实验。  
一个理想的智能体应当按如下流程行动：

1. 在主世界设置一个显式配置
2. 观察是否出现异常
3. 对异常进行主世界追踪
4. 进入对应隐世界搜集线索
5. 回到主世界继续做对照实验
6. 验证多个隐规则的叠加关系
7. 提交结构化报告

这比“随机乱试”更接近科学发现过程，也比“进入隐世界后系统直接告诉你答案”更像一个真正的 benchmark。
